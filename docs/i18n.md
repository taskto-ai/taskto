# Languages

taskto.ai is meant to work in everyone's language from the start. The web app shows every
string from a translation file, formats dates and numbers the user's way, and lays out
right-to-left scripts. This page is for contributors: how it works, how to add a string,
and how to add a language.

## Which language someone sees

1. The language they picked in the account menu (at the sidebar's foot), saved to their account
   (`PATCH /api/me`, [api.md](api.md)), so it follows them to other browsers.
2. Otherwise, the first of their browser's languages that taskto.ai has. A language
   matches its regional variants: a browser asking for `pt-PT` or `pt` gets `pt-BR`.
3. Otherwise, the workspace's default language, which admins set in Settings → General.
4. Otherwise, English.

The page's `lang` and `dir` follow it. The pick is also kept in the browser
(`localStorage`), so a reload shows it before the server answers.

## Where things are

| Path | What |
|---|---|
| `web/src/i18n/locales/en.json` | English, the reference: every key is here first |
| `web/src/i18n/locales/<tag>.json` | one file per language, named by its BCP 47 tag (`pt-BR.json`) |
| `web/src/i18n/index.tsx` | `useT()`, `useFormat()`, how the language is chosen, and loading a file |
| `web/scripts/i18n-check.mjs` | the CI check, and the report of what each language still lacks |

English is part of the app's main bundle. Every other file is loaded only when someone
picks it, as a chunk of its own. A key a language doesn't have yet shows in English.

## Writing a string

Never put text people see in a component. Add a key to `en.json`, under the area's group
(`shell`, `settings`, `boards`…), and use it:

```tsx
const t = useT()
return <button type="button">{t('boards.newCard')}</button>
```

Keys are checked when the app compiles: `t('boards.nweCard')` is a type error.

- **Placeholders**: `"greeting": "Hello, {name}"` with `t('greeting', { name })`. A
  number passed in is shown in the locale's digits (`1,234` or `1.234`).
- **Plurals**: a key per plural form, called without the suffix and with `count`:
  `"files_one": "{count} file"`, `"files_other": "{count} files"`, and
  `t('files', { count })`. English needs `_one` and `_other`; other languages have the
  forms `Intl.PluralRules` gives them (`_few` and `_many` in Polish, `_zero` to `_many`
  in Arabic). `_zero`, for exactly 0 ("No files"), is optional in any language.
- **Markup and links**: `t.rich()` returns React nodes. `<name>…</name>` in the message
  wraps its text with the function you pass as `name`, and a `{placeholder}` takes any
  node:
  ```tsx
  // "licence": "{name} by {by}, under <link>{licence}</link>."
  t.rich('about.licence', { name, by, licence, link: (text) => <a href={url}>{text}</a> })
  ```
  Don't build a sentence out of pieces: word order differs between languages, so give
  translators the whole sentence.
- **Dates, times, numbers, sizes, lists**: `useFormat()` (`f.dateTime(time)`,
  `f.relative(time)`, `f.number(n)`, `f.bytes(size)`, `f.list(names)`), never
  `toLocaleString()` or a format of your own.
- **Outside a component** (an error message built in a helper), `t()` from
  `web/src/i18n` gives the current language's text; it doesn't re-render on a change.
- **Names stay as they are**: the product's name, people's and workspaces' names, file
  names, tool names, and what users wrote are never translated.
- **Layout**: use logical CSS properties (`margin-inline-start`, `padding-inline-end`,
  `border-inline-start`, `inset-inline-end`, `text-align: start`), never `left` or
  `right`, so right-to-left languages mirror the layout. An icon that points a way
  (an arrow) may need flipping under `[dir="rtl"]`.

Biome's `noJsxLiterals` rule fails on text written directly in JSX anywhere in
`web/src` (tests aside: `overrides` in `biome.json`); text in attributes (`aria-label`,
`placeholder`, `title`), in constants and in errors thrown for people to read is up to
review.

Add the key to the other languages' files if you can; if not, leave it out, and it shows
in English until someone translates it. Never copy the English text into another file to
"fill it in": the report would count it as translated.

## Adding a language

1. Copy `web/src/i18n/locales/en.json` to `web/src/i18n/locales/<tag>.json`, where
   `<tag>` is the BCP 47 tag in its canonical case: `de`, `fr`, `es-419`, `zh-Hans`,
   `ar`.
2. Translate the values. Keep the keys, the `{placeholders}` and the `<tags>` exactly as
   they are; give each plural message the forms the language has (see Plurals above).
   You may leave keys out: they show in English.
3. Run `pnpm --filter @taskto/web run i18n`. It fails on a broken file and lists what is
   left untranslated.
4. Open a pull request. Someone who reads the language reviews it.

That's all: the app finds the file by its name, names the language in itself in the
menu ("Deutsch", "Français", "العربية"), and sets `dir="rtl"` for a script written right
to left (Arabic, Hebrew, Persian, Urdu and others, by the script of the tag).

## What CI checks

The CI job "Web + agent" runs `pnpm --filter @taskto/web run i18n`, which fails on:

- a key the code uses that `en.json` doesn't have;
- a key in another file that `en.json` doesn't have (renamed or removed in English);
- a translation with a `{placeholder}` English doesn't fill in, or different `<tags>`;
- a plural message with some of its language's forms but not all;
- a file that isn't nested objects of strings, or isn't named as a BCP 47 tag;
- an API error code without an `errors.<code>` message in `en.json`;
- the server, the web app and the agent runtime reading language tags with different
  patterns.

It then reports, without failing, how many messages each language has translated, and
the first untranslated keys (`--verbose` lists them all).

## Errors from the server

The server's errors carry a stable code beside their English message:
`{"error": "a name of 1 to 100 characters is required", "code": "name_length", "params": {"max": 100}}`
([api.md](api.md#error-codes)). The web app shows `errors.<code>` from the locale file,
with `params` filling its placeholders, so errors read in the user's language too
(`errorText()` in `web/src/api.ts`). A code the web app doesn't know yet shows the
server's English message.

To add an error in Go:

1. Add a constant to `internal/apierr/codes.go` (`CodeSpaceFull Code = "space_full"`),
   and a row to the table in `docs/api.md`.
2. Answer with `apierr.Write(w, status, apierr.CodeSpaceFull, "english message", apierr.Params{"max": n})`,
   or return an `*apierr.Error` from deeper code.
3. Add `"errors": {"space_full": "…"}` to `en.json` (and the other files if you can).

Tests fail on a code made from a string (`internal/apierr`), on a code missing from
`docs/api.md`, and CI on a code without a message in `en.json`. Errors only a broken
client can cause (a wrong enum, a missing field) share `bad_request`.

Text people see can also come in a successful answer: why a feature is off, a test of an
endpoint, a search's notices. Those answers carry the same codes beside their English
(`reason_code`, `code`, `notices`, [api.md](api.md)), and the web app shows them with
`codeText(code, params, english)`. Don't add a field of English for people to read
without a code beside it.

## The server's side

The server keeps each user's pick and each workspace's default (`users.locale`,
`workspaces.locale`). It accepts any tag of a language, a script and a region (not
variants or extensions), also one the web app has no file for, so a language can be picked
for the agent before the web app is translated into it. The server sends no text of its own
to show without a code that the web app translates (above). Email is the one text the server
does write: its templates are in `internal/mail/locales/<tag>.json`, one file per language named
by its BCP 47 tag like the web app's, with `en.json` the reference, and each message is rendered
in the recipient's language (the one they picked, else their workspace's default, else English).
A message a language lacks is English, and a test checks every file against English's
placeholders. Invites and reset links are still links an admin passes on until the features that
email them arrive ([install.md](install.md#email)).

## The agent and dictation

The agent replies in the user's language by default, and dictation listens for it. Each
message and each dictation the web app sends carries the browser's first language
(`browser_locale`, [api.md](api.md)), and the server picks the user's language
(`auth.Service.Language`, in `internal/auth/locale.go`):

1. the language the user picked in the account menu, even one the web app has no file for;
2. otherwise, the browser's language;
3. otherwise, the workspace's default;
4. otherwise none: the agent replies in the language the user writes in.

The server sends it to the agent runtime with the message, which keeps it with the
conversation and puts it in the system prompt as its `language` section
(`agent/src/language.ts`): reply in that language unless the user writes in another, and
write what you make for them (documents, cards, apps) in it too. A change, such as a new
pick in the account menu, reaches a conversation with its next message.

The system prompt's text and the tools' names and descriptions are English in every
language: models follow English instructions best, and the section names the user's
language in English and in itself ("Brazilian Portuguese (português (Brasil), pt-BR)"), so
nothing there needs translating. Adding a language needs nothing on the agent's side.

Conversations on a CLI worker (Claude Code, Codex, Grok Build) run the CLI with its own
system prompt, which taskto.ai doesn't change: those reply in the language the user writes
in.

Dictation uses the language's primary subtag (`pt` for `pt-BR`), when the workspace's
dictation settings name no language and the dictation doesn't ask to detect it
([dictation.md](dictation.md)). An engine that doesn't know the language detects it: the
local Parakeet model always does, and Whistle knows seven languages.
